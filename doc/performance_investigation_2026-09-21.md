### Вода

- Для миров с TerrainFoundation граф хранит связные затопленные узлы Slopes. Поиск ограничен макро-следом плюс кольцо; уровень ограничен порогом стока и согласован с выходящими руслами. Диагональное касание через сухую седловину не объединяет впадины.
- На этом пути GraphCarver не выкапывает чашу по макромаске и не поднимает искусственный rim. Старый путь сохранён для миров без фундамента. Пустой естественный бассейн не заменяется старой маской.
- Пространственный индекс включает расширение чаши и поддержку интерполяции берега. Версии: graph **13**, hydrology cache format **2**, baked-page generation **10**.
- Сохраняется гидравлический уровень на сухом берегу. `WaterTile::wet()` больше не считает ненулевую кодированную высоту признаком воды. Прибрежное покрытие океана не превращается в river flag.
- Частичный inland flag после фильтрации не означает океанский прибой. Геометрические волны уровня на реках и озёрах отключены, нормальная рябь сохранена.
- Исправлен 1-based lookup сегмента при аналитическом покрытии реки, включая последний ID.

Это ещё **не независимое от LOD поле воды**: вода использует индексы адаптивного террейна и его наборы данных. Узкие русла и переходы между телами требуют отдельного носителя и дальнейших проверок. Ограниченный flood не является полной гидродинамикой. Slopes сам уже содержит обработку мелких впадин.

## Подтверждённые ошибки и исправления

### 1. Меши деревьев перестали загружаться

В `src/engine/geometry/cluster_asset.cpp` к вершине оболочки добавили слой текстуры: 7 floats / 28 байт превратились в 8 floats / 32 байта. Версия файла осталась `SCC3`.

На диске шесть из семи файлов всё ещё имеют вершины по 28 байт:
- CommonTree_1 и Pine_1;
- обе соответствующие рощи;
- Rock_Medium_1 и Mushroom_Common.

Только Bush_Common уже записан с 32 байтами. Загрузчик отвергал остальные с `cluster sidecar size does not match what it declares`. В `scene_models_pass.cpp` отсутствие оболочки рощи включает fallback на импостер; для отдельных моделей теряется кластерная геометрия/оболочка.

**Исправлено:** новая запись использует SCC4; чтение поддерживает исходный SCC3 и переходный SCC3 с дополнит��льным полем. SCC4 имеет строгий размер. Для старого формата используется сохранённый общий слой оболочки — восстановить отсутствовавшие индивидуальные слои коры из старого файла невозможно, для них нужна пересборка ассетов.

Бесклиентный валидатор успешно прочитал **7/7 реальных файлов**. Ассеты не перезаписывались. Это восстановление доступности геометрии, не доказательство ускорения. Обычный mesh/impostor LOD-переход для отдельных объектов не удалён.

### 2. «CPU» в заголовке не включал основную работу кадра

`Runner::FrameTiming` учитывал fixed/setup/submit, но не EveryFrame-конвейеры, где выполняются подготовка террейна и сборка рендера. Заголовок складывал только эти малые слагаемые.

**Исправлено:** добавлен интервал `pipelines` и общий `cpu()`. В заголовке он виден как `work`. Это CPU wall-time внутри Runner без swapchain acquire, а не GPU timestamps и не полное время внешнего цикла ввода/UI.

`wait` не различает VSync и ожидание загруженного GPU. Высокий `wait` не доказывает, что уменьшение GPU-нагрузки бесполезно.

### 3. «100 тысяч треугольников» не были полным числом

`render_pipeline.cpp` исключал все indirect draws из `triangles`, хотя план моделей уже содержит точное `plan.triangles`. Таким образом, деревья и рощи вообще не попадали в этот показатель.

**Исправлено:** DrawItem может передать известное число indirect-треугольников. SceneModelsPass передаёт число из CPU-плана; общий счётчик и разбивка по проходам его учитывают.

У травы окончательное число после compute-culling остаётся на GPU. Для таких вызовов добавлен `unknownIndirectDraws`; заголовок показывает `>=` перед треугольниками и число `uncounted`. Блокирующего readback не добавлено. Нулевое количество инстансов теперь считается как ноль, а не как один.

## Что действительно остаётся в кадре

Работники строят страницы и меши, но не устраняют:
- сборку/сортировку инстансов, culling, выбор LOD и построение indirect-плана на главном потоке (`scene_models_pass.cpp`);
- обход и подготовку рощ, климатические выборки и создание корней при появлении нового меша;
- приём готовых страниц, GPU-загрузки, обновление таблиц резидентности и запись команд;
- GPU-работу по пикселям: материалы, освещение, вода, альфа-покрытие растительности, MSAA и обмен с памятью.

В `terrain_page_detail.hlsli` функция `pageShapeAt` вызывает `detailBedAt` девять раз. В обычном резидентном пути каждый вызов содержит чтение таблицы, высоты и полос детализации: по исходнику до 27 текстурных выборок на нормаль/кривизну, ещё до материалов. При переходе между наборами данных вычисляется и родительская форма. Это оценка структуры шейдера, не измеренный GPU bottleneck и не точное число аппаратных обращений после оптимизации компилятором.

Runner выбирает 4x MSAA, когда оно поддерживается. Это увеличивает нагрузку на покрытие/буферы; нельзя автоматически умножать стоимость каждого pixel shader на четыре.

Для 120 FPS бюджет кадра — 8,33 мс; для 60 FPS — 16,67 мс. «Осталось 60 FPS на симуляцию» следует выражать бюджетом миллисекунд: CPU и GPU частично перекрываются, FPS не складываются.

## Вода: что сделано, а что нет

### Озёра

В текущем `graph_carve.cpp` всё ещё существуют все три механизма из пользовательского рекапа:
1. `coverAt` интерполирует макроячейки; `ground` смешивает country и basinFloor по cover.
2. Rim при `0 < cover < 1/5` поднимает берег, до 3 м.
3. Идентификатор тела приходит из четырёх макроячеек; вне носит��ля маски он отсутствует.

Наличие последующей проверки `floor < basinLevel` этого не отменяет: проверяется уже изменённый маской рельеф. Slopes сейчас не заменяет этот lake floor. **В этом проходе гидрология не менялась.**

### Реки и шейдеры

`water_pages.hlsl` уже пересчитывает depth по текстурам на фрагменте. Но:
- `WaterPass` использует вершины/индексы адаптивного террейна, включая его waterIndices;
- `pageDetail` выбирает набор данных по ringState и смешивает его с родителем;
- для explicitSurface глубина всё равно заменяется значением из страницы, а затем WaterPS делает жёсткий clip по depth;
- попиксельная проверка не восстанавливает узкое русло, отсутствующее в выбранном наборе данных, и не исправляет макрорешёточную форму чаши.

То есть «вода уже в шейдере» и «берега независимы от геометрического LOD» — разные утверждения. Второе текущим кодом не обеспечено.

### Следующий обоснованный шаг

Сначала исправить источник данных, затем носитель отрисовки:
1. Использовать незаполненный Slopes для котловины, проверить уровень и связность с озером. Расширение области тела не должно затапливать соседнюю несвязанную впадину только из-за низкого минимума.
2. Из постоянного графа рек и озёр строить пространственно индексируемое поле воды: принадлежность, уровень, направление течения, расстояние до берега/покрытие. Его разрешение и фильтрация не должны следовать количеству треугольников земли. Не обходить весь граф на каждом пикселе.
3. Рисовать это поле на простой поверхности-носителе: плоскости для озёр, редкие полосы/патчи по профилю уровня для рек. Геометрию сохранять для настоящего перепада высоты, водопада, видимого русла и силуэта; один clip не меняет глубину и силуэт земли.
4. До визуальной проверки добавить CPU-регрессии: непрерывность узкой реки при смене LOD, замкнутость озера, приток/сток, соседние бассейны, межстраничные швы. Сам переход на поле в этом проходе не реализован.
